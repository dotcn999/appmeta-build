## ISS-01 未安装的描述文件仍被当成可用

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.inspect`，`InspectResult.ready`

### 现象

工程 `project.pbxproj` 里写了 `PROVISIONING_PROFILE_SPECIFIER`，但这份描述文件没有装在本机时，工具仍把它插进列表并选中。`ready` 只判断 `selectedProfile != nil`，占位对象也算数。界面上的 Archive 按钮可以点，导出阶段才被 xcodebuild 拒绝。

占位对象只写了 `kind`，没有把 `isAppStore` 设为 `true`。列表文案显示 App Store，上传按钮却按 `isAppStore` 保持禁用，两个判断互相矛盾。

### 解决方案

1. 区分「已安装」和「工程点名但缺失」。缺失项可以显示，但 `installed == false`，不能参与 `ready`。
2. `ready` 改为：已选描述文件来自本机文件、未过期、Bundle ID / Team 匹配、证书指纹与钥匙串有交集。
3. 占位项不要进入导出参数。用户选中缺失项时，按钮保持禁用，并在状态栏写明缺哪一份文件。
4. `kind == "appstore"` 时同步设置 `isAppStore`，或者删掉这个重复字段，只保留 `kind`。

### 验收

本机没有工程点名的 `.mobileprovision` 时，导出和上传都不可点，状态栏说明文件未安装。装上之后重新识别，按钮恢复。

### 处理记录

2026-10-08：未安装的描述文件只作提示，不参与可导出判断。过期、平台不明或证书指纹对不上时，导出按钮保持禁用。

## ISS-02 导出只覆盖一个 Bundle ID

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.pickSettings`、`XcodePipeline.exportOptionsPlist`

### 现象

`ExportOptions.plist` 的 `provisioningProfiles` 只有识别出来的那一个 Bundle ID。带 Widget、Share Extension、Watch App、App Clip 的工程，导出时其余 Target 没有对应描述文件。

`pickSettings` 会跳过名字里带 test 的 Target，然后采用第一份已经展开的 Bundle ID。扩展如果排在主 App 前面，主 App 的 Bundle ID 会被漏掉，描述文件字典的 key 也是错的。

### 解决方案

1. 用 `-showBuildSettings -json` 收集本次 scheme 里所有要签名的产品：主 App、扩展、App Clip。跳过纯测试 Target，保留 appex。
2. 每个 Bundle ID 各自匹配描述文件，全部写进 `provisioningProfiles`。
3. 任一需要签名的产品没有可用描述文件时，`ready = false`，并列出缺的 Bundle ID。
4. 界面展示这次会签名的产品列表，而不是只展示一个 Bundle ID。

### 验收

用一个包含 Widget Extension 的示例工程导出。`ExportOptions.plist` 里同时有主 App 和扩展的 Bundle ID，xcodebuild `-exportArchive` 成功。

### 处理记录

2026-10-08：从 build settings 收集主 App 和扩展。每个 Bundle ID 各自匹配描述文件，全部写入导出 plist。缺任何一个时不能导出。界面列出这些 Target。

## ISS-03 不支持 xcworkspace

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.resolveXcodeproj`

### 现象

路径以 `.xcworkspace` 结尾时直接抛错。CocoaPods、部分多工程仓库必须用 workspace 才能看到正确的 scheme 和依赖。只打开里面的 `.xcodeproj` 会缺 Pods target，Archive 失败。

### 解决方案

1. 识别结果保存容器类型：`project` 或 `workspace`。
2. `xcodebuild -list / -showBuildSettings / archive` 在 workspace 上使用 `-workspace`，不再传 `-project`。
3. 用户选中目录时，若同时存在 workspace 和 xcodeproj，优先 workspace，并在界面标明实际使用的文件。
4. 多个 workspace 时要求用户指定一个，避免猜错。

### 验收

对一个含 `Pods.xcodeproj` 的 workspace 执行识别和 Archive，命令行参数里是 `-workspace`，依赖 target 能编过。

### 处理记录

2026-10-08：支持直接选择 `.xcworkspace`。目录里如果有 workspace，优先用它。多个 workspace 时要求指定一个。Scheme 会到 workspace 和旁边的 xcodeproj 里找。

## ISS-04 Scheme 名称盖过真正的 Archive 配置

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.inferredConfigurationName`、`XcodePipeline.resolveConfiguration`

### 现象

配置名优先看 scheme 名字，而不是 `ArchiveAction` 的 `buildConfiguration`。

- 名字包含 `debug`、`develop`、`_dev`、`.dev` 时，用 LaunchAction 的配置，缺省 Debug。
- 名字包含 `release`、`prod`、`appstore` 时才用 ArchiveAction。
- `develop` 会命中 `Development`；`prod` 会命中 `Product` 这类无关名字。

因此名为 `Development`、ArchiveAction 实际是 Release 的 scheme，会被拿去按 Debug 识别证书和描述文件，Archive 也用 Debug。

### 解决方案

1. 解析 `xcshareddata/xcschemes` 和当前用户的 `xcuserdata/.../xcschemes` 里的 `ArchiveAction`。
2. Archive 配置只取 `ArchiveAction` 的 `buildConfiguration`。XML 缺失时再退回 Release。
3. 删掉按 scheme 名字猜 Debug/Release 的逻辑，或者仅在没有任何 scheme 文件时作为最后兜底，并且不要用 `contains("develop")` / `contains("prod")` 这种子串。
4. 界面同时显示「Archive 配置」和它来自哪个 scheme 文件。

### 验收

构造一个 scheme 名含 Development、ArchiveAction 为 Release、LaunchAction 为 Debug 的工程。识别结果的配置是 Release，后续 Archive 命令的 `-configuration` 也是 Release。

### 处理记录

2026-10-08：配置只读 scheme 的 ArchiveAction。读不到 scheme 文件时用 Release，不再按 scheme 名字猜 Debug。

## ISS-05 Ad Hoc / Enterprise 描述文件在 Release 下被隐藏

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.preferredProfileKinds`、`XcodePipeline.matchProfiles`

### 现象

配置名不含 `debug`、`adhoc`、`enterprise` 时，偏好类型只有 `appstore`。只要存在一份匹配的 App Store 描述文件，其余已安装的 Ad Hoc、Enterprise 描述文件会从列表里消失。

常见工程的 Archive 配置就叫 Release，Ad Hoc 包也用这份配置，只是换描述文件。这种工程在本机同时有 App Store 描述文件时，界面无法选出 Ad Hoc。

### 解决方案

1. 偏好类型只影响默认选中项和排序，不过滤掉其他类型。
2. 列表按类型分组：App Store、Ad Hoc、Development、Enterprise。
3. 默认选中与当前 Archive 用途一致的第一份未过期描述文件，用户仍可改选。
4. 导出方法继续跟「当前选中的描述文件类型」走，而不是跟配置名走。

### 验收

同一 Bundle ID 同时安装 App Store 和 Ad Hoc 描述文件，配置为 Release。两者都出现在选择器里，选中 Ad Hoc 后 `ExportOptions` 的 `method` 为 `ad-hoc`。

### 处理记录

2026-10-08：偏好类型只影响默认项和排序。App Store、Ad Hoc、Enterprise、Development 分组显示，选择后按该描述文件的类型导出。

## ISS-06 描述文件来源混杂，过期项优先

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.pbxprojProfileSpecifiers`、`XcodePipeline.matchProfiles`、`XcodePipeline.inspect`

### 现象

`pbxproj` 正则会抓出整个工程里所有 `PROVISIONING_PROFILE` / `PROVISIONING_PROFILE_SPECIFIER`，不区分 Target，也不区分 Debug 和 Release。这些名字一律标成 `match = project`，排序时压过本机按 Bundle ID 匹配到的描述文件。

过期判断只淘汰「非工程点名」的项。工程点名的过期描述文件会留在列表最前面，并成为默认选项。默认选中后又只对这一项做过期和证书指纹警告。

### 解决方案

1. 描述文件说明符改为从「当前 scheme + Archive 配置 + 对应 Target」的 build settings 读取，不再扫整份 pbxproj。
2. 工程点名只用于默认选中；本机其他匹配项仍保留在列表中。
3. 过期描述文件可以显示为禁用，不能成为默认项，也不能让 `ready` 为真。
4. 同一名字或 UUID 只保留一条，避免 SwiftUI `ForEach` 身份冲突。

### 验收

工程 Debug 与 Release 指定了不同描述文件。选择 Release scheme 时，默认描述文件是 Release 那一份；若它已过期，默认改到下一份未过期的匹配项，并明确提示原来那份已过期。

### 处理记录

2026-10-08：描述文件说明符只取当前 scheme 和 Archive 配置的 build settings。过期项不再当默认值。不再扫描整份 pbxproj。

## ISS-07 导出使用过期的识别结果

- 严重程度：高
- 状态：已解决
- 位置：`BuildEngine.runInspect`、`BuildEngine.runExport`、`ContentView` 工程路径输入框

### 现象

识别失败时只写入 `lastError`，不清除上一次的 `inspect`。`ready` 仍可能为真。

工程路径是可编辑文本框。用户改完路径后如果不重新识别，`runExport` 会用新路径配合旧的 configuration、team、bundle id、描述文件去 Archive。

识别开始时也不记录「这次结果对应哪条路径」。导出前没有断言 `inspect.projectPath == 当前路径` 且 scheme 属于这次结果。

### 解决方案

1. 每次开始识别时清空 `inspect`、`artifact` 和旧警告，避免失败后继续沿用。
2. 导出前在主线程核对：路径、scheme、配置、描述文件都属于同一次成功识别。不一致就拒绝执行并提示重新识别。
3. 路径文本框在识别成功后若被编辑，立刻把 `ready` 置为 false。
4. `busy == true` 时禁用路径编辑。

### 验收

先成功识别工程 A，再把路径改成工程 B 后直接点导出：操作被拒绝。让工程 B 识别失败：导出按钮不可用，界面不再展示工程 A 的签名信息。

### 处理记录

2026-10-08：开始识别时清掉上一次结果。成功后把路径改成实际打开的工程。路径和这次识别结果不一致时不能导出。

## ISS-08 后台线程读取界面状态

- 严重程度：高
- 状态：已解决
- 位置：`BuildEngine.runExport`、`BuildEngine.runUpload`、`BuildEngine.runInspect`

### 现象

`BuildEngine` 不是 `@MainActor`。`queue` 上的任务直接读 `self.projectPath`、`self.scheme`、`self.profile`。这些都是 `@Published` 的 `String`，主线程的 `TextField` 会同时写。Swift 字符串的 copy-on-write 不能跨线程读写。

构建进行中，scheme 和描述文件选择器是禁用的，工程路径框没有禁用，竞争窗口一直开着。

`run()` 若在 `current = proc` 之后抛错，`current` 不会被清掉，后续取消可能打到一个没启动的 `Process`。

### 解决方案

1. 把 `BuildEngine` 标成 `@MainActor`。进入后台队列之前，把路径、scheme、配置、team、bundle id、描述文件名、描述文件类型、凭证复制成值类型快照。
2. 后台任务只碰这个快照和 `XcodePipeline`，完成后再回主线程写 `inspect`、`log`、`artifact`、`lastError`。
3. 构建期间禁用路径框、凭证框和选择器。
4. `Process.run()` 用 `defer` 清理 `current`，保证启动失败也会放开锁状态。

### 验收

在 Archive 过程中连续修改路径框（修复前可复现的操作，修复后应已禁用）。用 Thread Sanitizer 跑一次识别加一次导出，不再报告 `projectPath` / `scheme` / `profile` 的数据竞争。

### 处理记录

2026-10-08：`BuildEngine` 改为 `@MainActor`。导出参数在主线程收成值类型后再进后台任务。构建期间禁用路径、密钥和选择按钮。`xcodebuild -scheme AppMetaBuild` 编译通过。

## ISS-09 子进程 stderr 未读取，识别错误被丢掉

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.runCapturing`、`XcodePipeline.parseList`、`XcodePipeline.decodeProfile`

### 现象

`runCapturing` 把 stderr 接到一条新 `Pipe()`，之后没有任何读取。管道缓冲区写满后，子进程会阻塞在写 stderr，`waitUntilExit` 永远等不到。`xcodebuild -list`、`-showBuildSettings` 都会往 stderr 打警告。`security cms -D` 对每份描述文件各跑一次，同样有未读取的 stderr。

失败时抛出的文本只来自 stdout。xcodebuild 的真正原因经常在 stderr，界面上就会看到空消息或无关 JSON。

`parseList` 要求整段 stdout 都是 JSON。xcodebuild 在 JSON 前面夹一行 warning 时，解析直接失败。`-showBuildSettings` 有跳到第一个 `[` 的容错，`-list` 没有。

### 解决方案

1. stdout 和 stderr 都接到管道并在独立读取端消费完，再 `waitUntilExit`。两条流都设上限，避免无限占用内存。
2. 非 0 退出时，把 stderr 的最后一段放进 `BuildError`。
3. 解析 `-list -json` 时，截取第一个 `{` 到最后一个 `}` 再交给 `JSONSerialization`。截取失败则展示原始输出的尾部。
4. 描述文件解码可以复用同一个解析函数，并对结果按文件修改时间做内存缓存，避免每次识别都对几百个 profile 调 `security cms`。

### 验收

让 xcodebuild 在 JSON 前输出一行警告，识别仍能得到 scheme 列表。让一个命令持续写超过 64KB 的 stderr，识别在有限时间内结束并显示这段错误，而不是一直停在「进行中」。

### 处理记录

2026-10-08：`CommandSession` 同时读完 stdout 和 stderr。失败信息优先取 stderr/stdout 尾部。`-list` JSON 允许前后杂质。描述文件按路径、修改时间和大小缓存。

## ISS-10 取消后进程还在，上传会自动重试

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.cancel`、`XcodePipeline.runStreaming`、`XcodePipeline.upload`、`BuildEngine.cancel`

### 现象

`cancel()` 只对 `current` 调用 `terminate()`。这只向该进程发 SIGTERM，xcodebuild 拉起的子进程不在同一个进程组里时会继续编译。

`runCapturing` 不登记 `current`。识别过程中点取消没有效果，`busy` 要等到 xcodebuild 自己结束。

`upload` 把 altool 的任何错误都当成「改用 iTMSTransporter 再传一次」。取消导致的非 0 退出也会走进这个分支，用户点了取消后仍会开始第二次上传。

取消成功时，状态栏用 `command failed (15): ...` 表示，和真正的构建失败同一套文案。应用退出时也没有先取消子进程。

### 解决方案

1. 启动子进程前建立新进程组（`setsid` / `setpgid`）。取消时向整个进程组发 SIGTERM，宽限后再 SIGKILL。
2. 增加显式的 `cancelled` 标志。识别、Archive、导出、上传每一步开始前都检查它。
3. 取消只终止当前步骤。`catch` 里若发现是取消，禁止启动 Transporter。
4. 状态栏在取消时显示「已取消」，保留已产生的日志和 IPA 路径。
5. 应用即将退出时走同一条取消路径，并给进程组留出结束时间。

### 验收

Archive 进行中点取消：几秒内 `pgrep -P` 看不到残留的 xcodebuild / swift-frontend，不会出现 Transporter 命令。上传进行中点取消：日志里只有一次上传命令。识别进行中点取消：`busy` 会结束。

### 处理记录

2026-10-08：子进程用 `POSIX_SPAWN_SETPGROUP` 单独成组，取消时对进程组先 SIGTERM 再 SIGKILL。识别、Archive、导出、上传开始前都看取消标志。altool 因取消失败时不会再启动 Transporter。状态栏显示「已取消」。退出应用时走同一条取消并等待最多 2.5 秒。

## ISS-11 日志会拖死界面，失败原因被藏起来

- 严重程度：高
- 状态：已解决
- 位置：`BuildEngine.appendLog`、`XcodePipeline.runStreaming`、`ContentView.logPane`

### 现象

每一次输出都执行 `log += line`。日志变长后，这是按总长度平方增长的拷贝。右侧用单个 `Text` 渲染整段日志，SwiftUI 会反复布局整份文本。一次正常 Archive 的输出足以让主线程卡住，取消按钮也随之点不到。

`readabilityHandler` 把不带换行的最后一段留在 `leftover`。进程结束时 handler 收到空数据就 return，这段不会刷出。随后单独读取剩余字节，又不会把 `leftover` 拼回去，最后一行会丢，跨两次回调的半行也会断掉。某个 UTF-8 字符被拆到两个 chunk 时，`String(data:encoding:)` 得到 nil，整个 chunk 被丢掉。

失败时 `lastError` 只有 `command failed (状态码): 命令行`。xcodebuild / ITMS 的可操作原因留在日志中部。

### 解决方案

1. 日志改为行数组或带上限的环形缓冲（例如保留最后 4000 行），用 `NSTextView` / `TextEditor` 追加，避免整段 `String` 反复拷贝和整树刷新。
2. 字节流按 `Data` 缓冲，遇到换行再按 UTF-8 解码；末尾不完整字节留到下一块。进程结束后强制刷出剩余文本。
3. 失败时把日志尾部中第一条 `error:`、`ITMS-`、`EXPORT FAILED`、`ARCHIVE FAILED` 抽进 `lastError`。状态栏允许选择和复制这段文字。
4. 完整日志写到本次产物目录的 `build.log`，界面只负责查看尾部。

### 验收

对一个会输出数万行的工程执行 Archive。窗口在输出过程中仍能滚动和点取消。故意制造签名错误时，红色状态栏出现 xcodebuild 的 error 行，而不是只有退出码。日志最后一行即使没有换行也能看到。

### 处理记录

2026-10-08：界面日志最多保留 4000 行，并用 `NSTextView` 显示。字节按行和 UTF-8 边界切分，进程结束时刷出最后一行。失败时把日志尾部第一条 `error:` / `ITMS-` / `EXPORT FAILED` / `ARCHIVE FAILED` 放进状态栏。完整输出写入本次产物目录的 `build.log`。

## ISS-14 API 私钥明文存放

- 严重程度：高
- 状态：未解决
- 位置：`CredentialsStore`、`XcodePipeline.prepareKeyDir`

### 现象

Key ID、Issuer ID 和私钥路径写在 `~/Library/Application Support/AppMeta Build/config.json`。`.p8` 被复制到同目录的 `private_keys/`。写入时没有把权限收成 `0600`，复制失败时还会退回使用用户选中的原始路径。

本应用关闭了 App Sandbox（调用任意工程的 xcodebuild 需要这么做），同用户下的其他进程可以读取这份私钥。App Store Connect API 私钥的权限通常足够上传二进制。

2. 若仍需临时文件给 altool / Transporter，写入后立即 `chmod 600`，目录 `0700`，放在用户独占的临时目录，并用 `defer` 加信号/退出钩子删除。
3. Key ID 只允许 10 位字母数字；Issuer ID 校验为 UUID。不合法就不保存、不拼路径。
4. 复制私钥失败时显示错误，不要静默改用原始路径。
5. 提供「从本机移除密钥」，同时删钥匙串项和旧的 `private_keys` 目录。

### 验收

保存密钥后，Application Support 下的 json 不含私钥内容，也没有可直接打开的 `.p8`。钥匙串里能看到对应项。Key ID 输入 `../x` 时保存被拒绝。上传使用的临时文件在命令结束后消失，权限为 `0600`。

## ISS-15 altool 失败后无条件再上传

- 严重程度：高
- 状态：已解决
- 位置：`XcodePipeline.upload`

### 现象

主路径是 `xcrun altool --upload-app`。只要退出码非 0，就立刻用 `iTMSTransporter -m upload` 再传同一个 IPA。这里面包括参数错误、认证失败、包本身被拒，以及 ISS-10 的取消。

3. 上传前确认 IPA 内的签名和 profile 类型是 App Store。Development / Ad Hoc 包在点击时就拒绝。
4. 解析 Transporter 输出里的 `ERROR` 行写入 `lastError`。退出码为 0 才显示「投递成功，等待 Apple 处理」。

### 验收

### 处理记录

2026-10-08：上传默认走 `iTMSTransporter`。只有找不到它时才用 altool。认证失败、包校验失败和取消都不会再传第二次。非 App Store 包在上传前被拒绝。

## ISS-16 证书匹配和导出证书名不一致

- 严重程度：中
- 状态：已解决
- 位置：`XcodePipeline.inspect` 证书段、`XcodePipeline.signingCertificate`、`XcodePipeline.identityFingerprints`

### 现象

钥匙串里只要有 `iPhone Distribution` 或 `iPhone Developer`，就会算作「有证书」，`ready` 可以为真。导出 plist 却把 `signingCertificate` 写死成 `Apple Distribution` 或 `Apple Development`。只有旧证书时，识别通过，导出失败。

指纹比对把描述文件里的证书和钥匙串里全部 codesign 身份做交集。描述文件若同时带了一张无关证书，而当前要用来签名的那张并不在文件里，警告不会出现。

旧证书名警告的条件不对称：`iphone developer` 用包含判断，`iphone distribution` 用整行小写后的全等。`iPhone Distribution: Company (TEAM)` 这种常见输出对不上全等，警告会漏掉。条件又把 Development 和 Distribution 证书用「或」连在一起，钥匙串里只有另一类证书时也会误报。

### 解决方案

1. 按描述文件类型选择期望证书：Development 用 Apple Development / iPhone Developer；App Store、Ad Hoc、Enterprise 用 Apple Distribution / iPhone Distribution。
2. `ready` 要求期望类别的证书存在，并且它的 SHA-1 在所选描述文件的 `DeveloperCertificates` 里。
3. 导出时 `signingCertificate` 写钥匙串里实际命中的那条身份名称，而不是固定的新名字。
4. 旧名字警告只比较「当前期望类别」和工程里的 `CODE_SIGN_IDENTITY`，用前缀匹配，覆盖带公司名的整行。

### 验收

只安装 `iPhone Distribution`、描述文件也包含该证书时，导出 plist 使用这条身份并且导出成功。描述文件不包含当前 Distribution 证书、但包含另一张在钥匙串里的证书时，`ready` 为 false，并提示证书不在描述文件中。

### 处理记录

2026-10-08：按描述文件类型匹配 Development 或 Distribution 证书，并用证书 SHA-1 和描述文件里的证书比对。导出和 Archive 使用钥匙串里的完整身份名称。旧证书名按前缀判断，且只比较当前需要的那一类。

1. 增加 macOS 单元测试 Target，把上述纯函数的输入输出固定下来。优先覆盖：通配 Bundle ID、过期描述文件排序、Release 下仍保留 Ad Hoc、ArchiveAction 优先于 scheme 名字、未知 kind 不生成 App Store plist、JSON 前有杂质时的 `-list` 解析、未展开的 `$` 设置。
2. 进程执行用协议包一层，测试里喂假的 stdout/stderr/退出码，验证取消不会触发第二次上传，以及 stderr 会被读完。

## ISS-23 文案语言在识别之后就固定了

- 严重程度：低
- 状态：未解决
- 位置：`AppearanceStore`、`L10n`、`XcodePipeline.inspect` 写入 `warnings` 的位置

### 现象

警告、阶段文字在识别或构建时就已经选好中文或英文，存进 `warnings` 和 `stage`。之后切换语言，这些字符串不会重算。

系统语言只要 `languageCode` 是 `zh` 就用简体文案，繁体中文环境也会拿到简体。

### 解决方案

1. `warnings` 改为稳定的错误码加参数，展示时再调用 `L10n`。
2. `stage` 同样存阶段枚举，界面按当前语言渲染。
3. 系统语言为 `zh-Hant` 时使用繁体文案；还没有繁体资源之前，保持英文，避免把繁体环境显示成简体。

### 验收

先识别出一个会出警告的工程，再切换语言，警告句子跟着变。系统语言设为繁体时，在未提供繁体文案前显示英文。

## ISS-24 图标缺失，产物路径不在界面上

- 严重程度：低
- 状态：未解决
- 位置：`Assets.xcassets/AppIcon.appiconset/Contents.json`、`ContentView.statusCard`

### 现象

App Icon 的 10 个 macOS 槽位都没有 `filename`，Dock 和程序坞里是空白图标。

导出成功后，状态区只有阶段文字。IPA 的绝对路径不在界面上，只能点「在 Finder 中显示」或到日志里找。上传失败时标题变成「失败」，路径更容易被忽略。

### 解决方案

1. 补一套 16 到 1024 的 macOS 图标并填进 asset catalog。
2. 状态卡在 `artifact` 非空时显示路径，支持选择复制。上传失败时保留这段路径，标题区分「IPA 已就绪，上传失败」和「Archive 失败」。

### 验收

运行后的 App 在 Dock 中有图标。导出成功和上传失败两种状态下，状态卡都能复制 IPA 路径。
